# 구현 계획

구현 구조와 순서의 기준 문서다. 기능 정책은 [요구사항 목차](../REQUIREMENTS.md)의 담당 문서에서만 관리하고 진행 상황은 [STATUS.md](../STATUS.md)를 따른다.

## 설계 상태

- 구조·스택은 사용자 추천안 위임으로 채택했다. 실제 라이브러리 버전은 구현 착수 시 공통 에디터와 호환성을 확인해 고정한다.
- 사용자 개발 시작 지시에 따라 1단계를 구현 중이다. 실제 코드·검증 위치는 [AGENTS.md](../AGENTS.md)의 바로가기를 따른다. 아래 전체 계획을 구현 완료 목록으로 해석하지 않는다.
- 외부 계약의 사실은 [플랫폼 자료](platform-integration.md), 실제 환경 미준비는 [운영 입력](operations.md#inputs)과 구분한다.

## 방법론 선택과 책임

끄적은 작성자 한 명의 콘텐츠 웹 서비스이며 공개 화면·관리 기능·비동기 업무를 가진다. **서버는 기능별 모듈 안에서 요청 처리와 업무 서비스를 나누고, 프런트는 파일 기반 라우팅과 화면별 구성을 사용한다.** 하나의 백엔드로 운영하면서 변경할 기능을 쉽게 찾을 수 있어 현재 범위에 적합하다.

NestJS의 [기능 모듈·공개 provider](https://docs.nestjs.com/modules)와 Next.js의 [프로젝트 구성](https://nextjs.org/docs/app/getting-started/project-structure)·[서버/클라이언트 경계](https://nextjs.org/docs/app/getting-started/server-and-client-components)를 확인해 정한 방향이다. 정확한 버전이 고정되면 달라진 계약만 재확인한다. 서버의 계층 구조를 UI에 그대로 적용하거나 헥사고날·클린 아키텍처의 추상화 계층을 일괄 도입하지 않는다.

| 구성 | 채택한 방식 | 책임 |
| --- | --- | --- |
| 웹 | Next.js·React·TypeScript | 공개/내 활동/관리자 화면·표시·접근성 |
| API | NestJS·TypeScript | 요청 검증·권한·업무 규칙·저장·외부 연동 |
| 데이터 | PostgreSQL | 관계·유일성·트랜잭션·서버 세션·영속 처리 기록 |
| 워커 | API와 같은 소스·이미지, 별도 실행 모드 | 플랫폼 Job 실행·자체 알림·전달 복구·정리 |
| 진입·배포 | Nginx·Docker Compose | [운영 기준](operations.md#deployment)의 진입·이미지·환경 분리 |

하나의 저장소와 하나의 블로그 백엔드로 시작한다. 향후 소스는 web/api와 기능별 영역으로 나누되 비어 있는 미래 폴더를 만들지 않는다. 기능별 마이크로서비스·별도 큐 서버·공통 플랫폼 기능 재구현은 하지 않는다. [자체 알림](users.md#notifications)은 사용자가 허용한 예외다.

- 화면 구성과 표시 처리는 web, 권한·공개 상태·저장 규칙은 api가 소유한다. 같은 규칙을 양쪽에 별도로 구현하지 않는다.
- API 진입점은 요청 검증·인증·응답 변환, 서비스는 업무 규칙·저장 흐름을 맡는다. 필요 없는 DB 추상화 계층·기본 클래스·단일 구현 인터페이스는 두지 않는다.
- 외부 연결 코드는 해당 연동 경계에 모으고 SDK·외부 응답 형식을 모든 기능에 퍼뜨리지 않는다. AI 생성 호출은 `ai/platform-ai.ts`, 실행 큐는 `ai/platform-jobs.ts`가 맡는다. 실제 중복이 확인된 코드만 공통화한다.
- 공개/본인/관리자/자동화 진입점은 업무 권한으로 구분한다. 같은 글 저장은 공통 업무 서비스를 사용한다.
- 함수·변수는 업무 의미로 이름 짓고 복잡한 조건은 읽기 쉽게 푼다. 주석은 반복 설명보다 정책의 이유를 적는다.
- DB 제약·트랜잭션·버전이 있는 마이그레이션을 사용한다. 운영에서 수동 SQL 변경에 의존하지 않는다.
- 수치는 해당 기능의 설정 또는 명명된 상수에 모으되 모든 값을 관리자 설정 화면으로 만들지는 않는다.

## 코드 배치와 의존 방향

아래는 전체 구현의 배치 기준이다. `apps/web/src/app`, `components`, `lib`와 `apps/api/src/auth`, `posts`, `database`가 생성됐다. 나머지 기능 폴더는 구현할 때 만든다. 실제 탐색은 AGENTS.md의 연결을 따른다.

| 예정 영역 | 넣을 것 | 넣지 않을 것 |
| --- | --- | --- |
| `apps/web/src/app` | App Router 진입·레이아웃·화면 조합, 해당 경로 전용 화면/상태를 가까이 배치 | DB 직접 접근·업무 권한의 최종 판정 |
| `apps/web/src/components` | 실제로 여러 화면이 사용하는 표현 컴포넌트 | 한 화면만 쓰는 로직·앞으로 공유할 것 같은 코드 |
| `apps/web/src/lib` | 책임이 명확한 API 접근·서버 설정 연결 | 관련 없는 코드를 모은 범용 utils |
| `apps/api/src/<기능>` | 글·인증·댓글 등 기능의 controller·service·입력 계약 | 다른 기능의 내부 데이터 처리를 임의로 수정하는 코드 |
| 기능별 외부 연결 파일 | 플랫폼/n8n 요청·응답 변환·통신 오류 처리. AI Job은 `ai/platform-jobs.ts` | 공개 상태·요약 반영 여부 같은 업무 정책 |
| API의 worker 진입 | 기존 업무 서비스를 호출하는 작업 실행·수명 관리 | HTTP controller 호출·업무 규칙 복사 |

AI 도우미는 `apps/api/src/ai`에 설정·입력 계약·업무 서비스·작업 실행을 모은다. 기존 worker 안에서 일반 작업과 호출 전용 작업을 독립 소비하며 추가 큐 서버는 만들지 않는다. 사람과 AI의 초안 생성은 `posts/create-draft.ts`의 검증·저장을 공유한다. n8n 워크플로 생성·등록은 로컬 `scripts`에 두고 관리 키는 실행 컨테이너에 전달하지 않는다.

내 활동은 `me`에서 본인 목록 조회·표시 닉네임 설정을 담당하고, `settings`는 광고 설정과 사이트 기본 정보·검색 인증·방문 분석을 기능별 서비스로 관리한다. 광고 서비스·발급값·스위치는 관리자 설정에서 저장하고 초기 환경값은 API가 소유한다. 공개 화면은 검증된 위치별 광고 정보만 받고 서비스별 SDK 실행은 각 표시 컴포넌트에 둔다. 사이트 설정 조회는 서버 렌더링 요청 안에서 재사용하고 인증 메타와 사이트 정보의 기준값을 공유한다. 알림은 `notifications`에서 수신자별 처리 기록·전달·읽음·보존을 담당한다. 댓글 서비스는 같은 트랜잭션으로 알림 처리 기록을 남긴다. 워커는 API 이미지를 재사용해 해당 서비스를 호출하며 별도 큐나 플랫폼 추상화 계층을 추가하지 않는다. 원문 위치는 댓글 서비스가 현재 정렬·공개 상태를 기준으로 계산한다.

- 웹의 경로/화면은 필요한 컴포넌트·API 클라이언트를 사용한다. 서버 데이터의 기준은 API이며 화면 상태와 서버 데이터를 구분한다. 편집기·상호작용만 필요한 클라이언트 경계에 둔다. 전체 화면을 관성적으로 클라이언트 코드로 만들지 않는다.
- API 의존 방향은 요청/작업 진입 → 기능 서비스 → DB 또는 외부 클라이언트다. 하위 데이터·통신 코드에서 상위 controller나 업무 서비스를 역참조하지 않는다.
- 다른 기능은 모듈이 공개한 서비스만 사용한다. 내부 구현 파일을 깊은 경로로 참조하거나 서로 양방향으로 의존하지 않는다. 순환이 필요해 보이면 먼저 책임과 호출 흐름을 조정한다.
- DB 접근 코드는 기능 서비스 안에서 시작하고 복잡성·재사용 필요가 확인될 때 분리한다. 모든 기능에 형식적인 repository/interface 계층을 요구하지 않는다.
- `shared/common/utils`는 실제 공유와 명확한 책임이 확인된 경우에만 둔다. 함수·파일 분리는 크기가 아니라 책임·변경 이유·가독성으로 판단한다.
- 새 기능은 요구사항의 기준 위치 → 예정/실제 코드 위치 → 의존 관계 → 수용 조건 순서로 확인한다. 기본 구조를 바꿔야 할 때만 대안·이유·영향을 짧게 제시한다.

UI 작업은 채택한 방향 안에서 화면·상호작용을 먼저 정리하고 필요한 범위의 디자인 스킬을 사용한다. 검수 문제를 모아 수정한 뒤 확인하며 끝없는 미세 조정을 반복하지 않는다.

## 검증과 완료 기록

- 변경한 기능의 수용 조건과 영향 범위에 맞춰 검사한다. 권한·공개 범위·중복 요청·저장 충돌·장애 복구처럼 실패 영향이 큰 동작을 우선한다.
- 문서만 바꾼 작업은 링크·정책 일관성을 확인하며 실행되지 않은 앱 테스트를 추가하거나 통과로 보고하지 않는다.
- 실제 실행/테스트 명령은 환경이 생긴 뒤 검증해서 기록한다. 아직 없는 명령을 예시로 만들어 AGENTS.md에 넣지 않는다.
- 로컬 구현 검증과 실계정·운영 배포·복원 검증을 구분한다. 외부 환경이 준비되지 않은 검수는 미완료로 남긴다.
- 의미 있는 작업 단위마다 기준 문서와 STATUS.md를 갱신하고 완료 상세는 [이력](history.md)으로 옮긴다. 일반 진행 로그를 쌓지 않는다.
